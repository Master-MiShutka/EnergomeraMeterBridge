# Energomera Meter Bridge — документация

Полная документация аддона Home Assistant для опроса электросчётчика
**Энергомера CE301(BY)** через TCP-шлюз по протоколу IEC 61107
(ГОСТ Р МЭК 61107-2001, режим C) с публикацией результатов в MQTT
и автоматическим созданием сущностей.

**Версия:** 1.1.0 · **Slug:** `meter_bridge` · **Архитектуры:** `aarch64`, `amd64`

Документация написана по официальной инструкции по программированию счётчиков
Энергомера CE301/CE303: сверены приложение А (форматы параметров и команд),
п. 5.2 (уровни доступа и пароли) и п. 5.3.2 (быстрое выборочное чтение). Сама
инструкция в репозитории не публикуется — это документ производителя, скачайте
его на официальном сайте Энергомера. Ссылки на пункты и таблицы инструкции
приведены по тексту.

## Как это работает

```text
┌──────────────┐   IEC 61107    ┌──────────────┐    TCP     ┌──────────────────┐
│ CE301(BY)    │ ◄────────────► │ TCP-шлюз     │ ◄────────► │ meter_bridge.py  │
│ (счётчик)    │  (оптопорт /   │ (RS-485 →    │            │ (аддон)          │
└──────────────┘   RS-485)      │  Ethernet)   │            └────────┬─────────┘
                                └──────────────┘                     │ MQTT
                                                                     ▼
                                                            ┌──────────────────┐
                                                            │ MQTT-брокер      │
                                                            └────────┬─────────┘
                                                                     │ AutoDiscovery
                                                                     ▼
                                                            ┌──────────────────┐
                                                            │ Home Assistant   │
                                                            └──────────────────┘
```

Цикл работы аддона:

1. При старте читаются параметры из `/data/options.json` (файл создаёт Supervisor),
   формируется конфигурация и открывается соединение с MQTT-брокером.
   Если брокер недоступен, аддон ждёт его, а не завершается с ошибкой.
2. Discovery-конфигурации публикуются в `on_connect` — то есть при первом
   подключении и при каждом переподключении.
3. Далее в цикле: открывается TCP-соединение со счётчиком, последовательно
   читаются все включённые параметры, значения публикуются в MQTT, соединение
   закрывается.
4. Пауза до следующего цикла; сон разбит на секундные интервалы, чтобы аддон
   быстро реагировал на `SIGTERM` при остановке или перезапуске.
5. Ошибка любого цикла логируется, в `{topic_prefix}/status` публикуется `offline`,
   и попытка повторяется на следующей итерации — аддон не завершается.

Все значения публикуются с флагом `retain`, поэтому подписчик сразу получает
последнее известное значение, даже если аддон сейчас перезапускается.

## Нужен ли пароль администратора

**Короткий ответ: для работы аддона пароль администратора не нужен.** Аддон только
читает данные, а все используемые параметры доступны на пользовательском уровне
доступа. Пароль требуется лишь в необязательном режиме `read_mode: session` и лишь
в том случае, если в счётчике включено парольное выборочное чтение.

Обоснование по тексту инструкции:

1. **Аддон ничего не программирует.** Таблица А.4 «Кодировка массива
   программируемых параметров» (с. 56) содержит только дату/время, конфигурацию,
   тарифные расписания, пароли и служебные параметры. Ни `ET0PE`, ни `ENMPE`,
   ни `EADPE`, ни `MAXPE`, ни `POWEP`, ни `VOLTA`, ни `CURRE` в неё не входят —
   это параметры «только чтение».
2. **Все семь команд доступны пользовательскому уровню.** Они перечислены в
   таблице А.3 «Кодировка массива параметров, выводимых через интерфейс при общем
   и выборочном чтении» (с. 55), которая описывает вывод параметров «для
   пользовательского уровня доступа»:

   | Параметр | Группа | Бит |
   | --- | --- | --- |
   | `ET0PE` | 1 | 11/2048 |
   | `ENMPE` | 2 | 3/8 |
   | `EADPE` | 3 | 11/2048 |
   | `MAXPE` | 4 | 10/1024 |
   | `POWEP` | 5 | 11/2048 |
   | `VOLTA` | 6 | 1/2 |
   | `CURRE` | 6 | 0/1 |

3. **Беспарольное чтение — штатный режим.** П. 5.2: «Счетчик имеет 2 пароля для
   реализации различных уровней доступа выборочного чтения и программирования:
   пароль администратора и пароль пользователя», причём «выборочное чтение для
   пользователя может быть парольным или беспарольным».
4. **Что именно переключает этот режим.** Параметр `CONDI` (таблица А.1, с. 45–46):

   | Бит | Значение | Смысл |
   | --- | --- | --- |
   | 0 | `0` | выборочное чтение **беспарольное** |
   | 0 | `1` | выборочное чтение парольное (пользователем по списку `LISTR`) |
   | 8 | `0` | программирование разрешается после нажатия кнопки «ДСТП» |
   | 8 | `1` | программирование разрешается **без** нажатия «ДСТП» |

5. **П. 5.5 подтверждает то же для ПО AdminTools:** «Если пароль не указан, то в
   программе можно выполнять только чтение, при этом в счетчике должно быть
   установлено разрешение на беспарольное чтение».

### Что аддон делал неправильно до версии 1.0.5

Аддон открывал сессию обмена и запрашивал **режим программирования**
(`program_mode()`, символ режима «1»). Счётчик разрешает программирование только
после снятия аппаратной блокировки пломбируемой кнопкой «ДСТП» (`CONDI`, бит 8 = 0)
либо при установленном бите 8. Поэтому на счётчике с включённой аппаратной
блокировкой аддон не читал ничего — хотя чтение было разрешено. Дополнительно
опция `meter_password` нигде в коде не использовалась: пароль нельзя было передать,
даже если он был известен.

### Как сделано в версии 1.0.5

По умолчанию используется **быстрое выборочное чтение вне сеанса** — штатный
механизм из п. 5.3.2 инструкции:

```text
/?!<SOH>R1<STX>ИМЯ_ПАРАМЕТРА()<ETX><BCC>          — безадресная команда
/?адрес!<SOH>R1<STX>ИМЯ_ПАРАМЕТРА()<ETX><BCC>     — адресная команда
```

Сессия не открывается, режим программирования не запрашивается, пароль не нужен.
Счётчик отвечает кадром `<STX>данные<ETX><BCC>`, из которого извлекаются числа
в круглых скобках.

### Если в счётчике включено парольное выборочное чтение

`CONDI`, бит 0 = 1 означает, что выборочное чтение защищено паролем. В этом случае:

- оставьте `read_mode: fast` и укажите пароль в `meter_password` — аддон передаст
  его в `authorize()` (`<SOH>P1<STX>(пароль)<ETX><BCC>`) и продолжит читать
  безадресными кадрами; либо
- переключите `read_mode: session` и укажите `meter_password` — при этом счётчик
  должен разрешать программирование (`CONDI`, бит 8 = 1 или нажатие «ДСТП»).

Подойдёт пароль пользователя, если администратор внёс нужные параметры в список
`LISTR`; иначе нужен пароль администратора. Напоминание из п. 5.2: на сутки даётся
3 попытки ввода пароля без нажатия кнопки «ДСТП» и 3 попытки после нажатия.

> **Вывод:** для чтения всех данных аддона пароль администратора не требуется при
> `CONDI`, бит 0 = 0 (беспарольное выборочное чтение). Если бит 0 = 1, нужен пароль
> (пользователя или администратора). Значение `CONDI` можно прочитать тем же
> аддоном или ПО AdminTools в разделе «Конфигурация» → «Интерфейсный обмен».

## Требования и подготовка

| Компонент | Требование |
| --- | --- |
| Home Assistant | Home Assistant OS или Supervised (аддон читает `/data/options.json` и без Supervisor не запускается) |
| Архитектура хоста | `aarch64` (64-битный ARM) или `amd64` (x86-64). 32-битные `armv7`/`armhf`/`i386` **не поддерживаются** |
| Счётчик | Энергомера CE301(BY), поддерживающий IEC 61107 и интерфейс чтения (оптопорт / RS-485). С CE303 аддон также должен работать — набор параметров совпадает, но совместимость не проверялась |
| Шлюз | TCP-шлюз или конвертер «последовательный порт → Ethernet», подключённый к интерфейсу счётчика |
| Брокер | MQTT-брокер, например официальный аддон **Mosquitto broker** |
| Сеть | Аддон работает с `host_network: true`, поэтому видит локальную сеть и может обращаться к шлюзу счётчика |

Перед установкой убедитесь, что:

- шлюз доступен по сети и его TCP-порт открывается;
- известен сетевой адрес (IDPAS) счётчика (заводское значение — `777777`);
- в Home Assistant настроена интеграция **MQTT** (она нужна для появления сущностей).

## Установка

1. **Настройки → Дополнения → Магазин**.
2. **⋮** → **Репозитории** → вставьте адрес и нажмите **Добавить**:

   ```text
   https://github.com/Master-MiShutka/EnergomeraMeterBridge
   ```

3. Обновите страницу магазина, откройте **Energomera Meter Bridge** → **Установить**.
4. Вкладка **Настройки** — заполните параметры из таблицы ниже → **Сохранить**.
5. Вкладка **Журнал** — убедитесь, что в логе есть `MQTT connected` и строки
   `Read <команда> (<ключ>) = ...`. Затем проверьте появившиеся сущности.

## Параметры конфигурации

### Подключение к счётчику

| Параметр | Тип | По умолчанию | Описание |
| --- | --- | --- | --- |
| `meter_host` | строка | `192.168.10.250` | IP-адрес TCP-шлюза, подключённого к счётчику |
| `meter_port` | порт | `1111` | TCP-порт шлюза |
| `meter_address` | строка | `777777` | Сетевой адрес (IDPAS) счётчика |
| `meter_password` | пароль | `777777` | Пароль счётчика. **Для чтения не требуется**; применяется только при `read_mode: session` или при парольном выборочном чтении. Заводское значение — `777777` |
| `read_mode` | список | `fast` | `fast` — быстрое выборочное чтение вне сеанса, пароль не нужен. Поддерживается не всеми счётчиками: CE301 v11 такие кадры игнорирует. `session` — сессия обмена в режиме программирования (поведение 1.0.4), требует разрешения программирования. `array` — сеанс в режиме чтения с разбором массива общего чтения; работает там, где `fast` и `session` данных не дают (см. [«Режим array»](#режим-array-массив-общего-чтения)) |
| `use_address` | логический | `false` | Отправлять кадры чтения с сетевым адресом счётчика: `/?<IDPAS>!<SOH>R1…` вместо безадресного `/?!<SOH>R1…`. Включайте, если TCP-шлюз обслуживает несколько счётчиков на одной шине и игнорирует безадресные кадры |
| `emulate_parity` | логический | `true` | Эмуляция 7E1 в 8N1: байты с нечётным числом единичных бит получают установленный 8-й бит. Оставьте включённой для шлюзов, эмулирующих 7E1; выключите для прозрачных 8N1-шлюзов |

### Флаги чтения

Выключение флага исключает соответствующие сущности из опроса и из discovery.
Перезапускайте аддон после изменения флагов: discovery публикуется при подключении
к брокеру.

| Параметр | Тип | По умолчанию | Что включает |
| --- | --- | --- | --- |
| `read_energy` | логический | `true` | Накопленная активная энергия (`ET0PE`), всего и по T1–T5 |
| `read_power` | логический | `true` | Мгновенная активная мощность (`POWEP`) |
| `read_voltage` | логический | `true` | Напряжение по фазам A, B, C (`VOLTA`) |
| `read_current` | логический | `true` | Ток по фазам A, B, C (`CURRE`) |
| `read_monthly_archive` | логический | `true` | Энергия на конец предыдущего месяца (`ENMPE`) — «медленный» |
| `read_daily_archive` | логический | `true` | Расход за каждый из последних 7 суток (`EADPE`) — «медленный»; в режиме `array` не действует (см. [«Режим array»](#режим-array-массив-общего-чтения)) |
| `read_max_power` | логический | `true` | Максимум мощности за текущий месяц (`MAXPE`) — «медленный» |
| `read_device_info` | логический | `true` | Заводской номер счётчика (`SNUMB`), сетевой адрес, модель и версия ПО. Только для режима `array`: раз в сутки один цикл дочитывает массив до конца (≈42 с вместо ≈21 с), найденное кэшируется в `/data/device_info.json` |

## Сущности и MQTT-топики

Discovery-топик каждой сущности:

```text
homeassistant/sensor/{node_id}/{topic_base}[/{suffix}]/config
```

где `node_id` — значение опции `node_id` либо `meter_<meter_address>`
(например, `meter_777777`). Состояние публикуется в:

```text
{topic_prefix}/{topic_base}[/{suffix}]
```

### Быстрый цикл

| Команда | Значение | `topic_base` | Суффиксы | Единица | Device class / state class | Имя сущности |
| --- | --- | --- | --- | --- | --- | --- |
| `ET0PE` | Активная энергия | `et0pe` | `total`, `t1`…`t5` | kWh | `energy` / `total_increasing` | Active energy total, Active energy T1…T5 |
| `POWEP` | Активная мощность | `powep` | — | W | `power` / `measurement` | Active power |
| `VOLTA` | Напряжение | `volta` | `a`, `b`, `c` | V | `voltage` / `measurement` | Voltage A, Voltage B, Voltage C |
| `CURRE` | Ток | `curre` | `a`, `b`, `c` | A | `current` / `measurement` | Current A, Current B, Current C |

### Медленный цикл

| Команда | Аргумент | Значение | `topic_base` | Суффиксы | Единица | Имя сущности |
| --- | --- | --- | --- | --- | --- | --- |
| `ENMPE` | последний завершённый месяц, `мм.гг` | Энергия на конец месяца | `enmpe` | `total`, `t1`…`t5` | kWh | Energy at month start total, … T1…T5 |
| `EADPE` | `дд.мм.гг`, 7 команд: 1…7 дней назад | Расход за сутки | `eadpe_d0`…`eadpe_d6` | `total`, `t1`…`t5` | kWh | Расход 1 дн. назад total, … T1…T5 |
| `MAXPE` | текущий месяц, `мм.гг` | Максимум мощности | `maxpe` | `t1`…`t5` | W | Maximum power T1…T5 |

В режиме `array` дополнительно публикуется показание на начало **предыдущего**
месяца — запись месячного кольца на месяц раньше (см.
[«Режим array»](#режим-array-массив-общего-чтения)):

| Команда | Значение | `topic_base` | Суффиксы | Единица | Имя сущности |
| --- | --- | --- | --- | --- | --- |
| `ENMPE` (предыдущий месяц) | Показание на начало прошлого месяца | `enmpe_prev` | `total`, `t1`…`t5` | kWh | Energy at previous month start total, … T1…T5 |

### Диагностика

| Команда | Значение | `topic_base` | Единица | Имя сущности |
| --- | --- | --- | --- | --- |
| `SNUMB` | Заводской номер счётчика | `serial` | — | Serial number |

Публикуется только в режиме `array` и только при `read_device_info: true`; в Home
Assistant попадает в раздел «Диагностика» карточки устройства, а сам номер — ещё и
в поле «Серийный номер» устройства.

Особенности:

- **Шесть значений у энергии.** По таблице А.1 параметр `EXYZT` «выдается массивами
  по 6 одноименных параметров, из которых первый – суммарная энергия, а второй –
  шестой – энергия, накопленная соответственно в период действия первого – пятого
  тарифов». Поэтому у `ET0PE`, `ENMPE` и `EADPE` по шесть сущностей: `total` и
  `t1`…`t5`. Если счётчик настроен на меньшее число тарифов, лишние топики просто
  не публикуются.
- **Пять значений у максимумов.** `MAXyz` выдаёт максимумы «по каждому тарифу
  (5 значений)» — без суммарного, поэтому у `MAXPE` суффиксы `t1`…`t5`.
- **Масштабирование.** Значения `POWEP` и `MAXPE` умножаются на 1000 (кВт → Вт),
  поэтому в Home Assistant мощность отображается в ваттах.
- **`unique_id`** формируется как `{node_id}_{topic_base}[_{suffix}]`,
  например `meter_777777_et0pe_t1`. Идентификатор зависит от `meter_address`
  (или заданного `node_id`): после его изменения Home Assistant создаст новое
  устройство, а старые сущности нужно удалить вручную — см.
  [«Смена node_id»](#смена-node_id-почему-появляется-второе-устройство).
- **Дубли по ключу.** `EADPE` читается 7 раз с разными аргументами, поэтому у неё
  отдельные ключи `EADPE_d0`…`EADPE_d6` и отдельные `topic_base`.
- **Имена сущностей — английские** («Active energy total», «Расход 1 дн. назад»).
- **Доступность.** Каждая сущность объявляет `availability_topic` =
  `{topic_prefix}/status` с payload `online`/`offline`, поэтому при потере связи с
  брокером или счётчиком сущности становятся «недоступными» (значения при этом
  сохраняются как последние известные).

### Смена `node_id`: почему появляется второе устройство

Discovery-топик и `unique_id` каждой сущности содержат `node_id`:

```text
homeassistant/sensor/{node_id}/{topic_base}[/{suffix}]/config
```

`node_id` по умолчанию — `meter_<meter_address>`. Если он меняется (или менялся
`meter_address`, или вы обновились с версии, где идентификатор был другим), аддон
публикует конфигурации уже под новым именем. Home Assistant видит новые
`unique_id` и создаёт **второе устройство**; старое остаётся со своими сущностями.

Признак этой ситуации в MQTT Explorer: в `homeassistant/sensor` лежат два узла —
например `main_meter_ce301` (старый, набор сущностей прошлых версий) и
`meter_777777` (текущий). Значения обеих групп берутся из одних и тех же топиков
`{topic_prefix}/…`, поэтому старое устройство выглядит «живым», но новых сущностей
(`et0pe_t4`/`t5`, `enmpe_*`, `maxpe_*`, `serial`) в нём нет.

Что делать — выберите одно:

**Оставить текущий идентификатор (`meter_<адрес>`).** Удалить старое устройство
в Home Assistant (**Настройки → Устройства** → устройство → **Удалить**) и
очистить его retained-конфигурации, иначе оно вернётся после перезапуска HA:

```yaml
# Настройки → Устройства и службы → MQTT → «Опубликовать пакет»
topic: "homeassistant/sensor/main_meter_ce301/et0pe_total/config"
payload: ""
retain: true
```

Так нужно пройти по всем старым config-топикам. Быстрее — MQTT Explorer: раскрыть
узел старого устройства и удалить retained-топики, либо скриптом:

```python
import time, paho.mqtt.client as mqtt
from paho.mqtt.client import CallbackAPIVersion

PREFIX = "homeassistant/sensor/main_meter_ce301/#"   # что чистим
HOST, PORT, USER, PASSWORD = "192.168.10.7", 7586, "mosqq_meter", "…"

topics = []
c = mqtt.Client(CallbackAPIVersion.VERSION2, client_id="cleanup")
c.username_pw_set(USER, PASSWORD)
c.on_connect = lambda *a: c.subscribe(PREFIX, 0)
c.on_message = lambda cl, u, m: topics.append(m.topic)
c.connect(HOST, PORT, 30); c.loop_start(); time.sleep(5); c.loop_stop()
for t in topics:
    c.publish(t, payload="", retain=True)      # пустой retained = удалить
print("удалено топиков:", len(topics))
```

**Вернуться к старому идентификатору** (если жаль истории и статистики уже
существующих сущностей): укажите его в опции `node_id` (например,
`main_meter_ce301`) и очистите узел, который стал лишним. Существующие сущности
сохранят свои `entity_id` и историю, а недостающие (`et0pe_t4`/`t5`, `enmpe_*`,
`maxpe_*`, `serial`) появятся в том же устройстве.

Общее правило: **сначала останавливайте приложение**, потом чистите retained —
иначе при следующем подключении оно само вернёт свои конфигурации. В режиме
`array` суточные сущности (`eadpe_d*`) не публикуются, поэтому их config-топики
также стоит убрать, если они остались от режимов `fast`/`session`.

### Пример

При `topic_prefix: main_home_meter` и `meter_address: "777777"`:

```text
main_home_meter/status                 → online
main_home_meter/powep                  → 1234.0
main_home_meter/volta/a                → 231.5
main_home_meter/curre/b                → 3.12
main_home_meter/et0pe/total            → 53309.45
main_home_meter/et0pe/t1               → 9342.39
main_home_meter/enmpe/total            → 53100.20
main_home_meter/eadpe_d0/total         → 12.34
main_home_meter/maxpe/t1               → 5432.0

homeassistant/sensor/meter_777777/powep/config
homeassistant/sensor/meter_777777/et0pe_t1/config
```

## Тарифы и стоимость в панели «Энергия»

Аддон публикует каждый тариф отдельной сущностью с `device_class: energy` и
`state_class: total_increasing` (`et0pe/t1`, `et0pe/t2`, `et0pe/t3`), поэтому
Home Assistant считает затраты по тарифам без дополнительных помощников:

1. **Настройки → Панели → Энергия → Электрическая сеть → Подключения к сети.**
2. Если раньше было добавлено подключение по суммарной энергии
   (`Active energy total`), удалите его — иначе расход посчитается дважды.
3. Добавьте по подключению на каждый тариф (`Active energy T1`, `T2`, `T3`) и в
   каждом укажите свою цену за кВт·ч (блок стоимости → фиксированная цена).
4. Валюта для затрат берётся из **Настройки → Система → Общие → Валюта**.

Панель считает расход по приращениям счётчика, поэтому тарифные регистры, в
которых лежит постоянная величина (на проверенном CE301 в `t4` зафиксировано
474,0064902 кВт·ч, `t5` = 0), можно не подключать: на суточные и месячные цифры
они не влияют.

Если счётчик не отдаёт тарифные регистры (или его зоны не совпадают с зонами
биллинга), [документация Home Assistant](https://www.home-assistant.io/docs/energy/faq/#split-consumption-by-tariffs)
предлагает делить потребление на тарифы интеграцией `utility_meter`: создаётся
селектор текущего тарифа и автоматизации на каждую зону. Для этого аддона такой
путь не нужен — тарифы приходят с самого счётчика.

Порядок важен: сначала завершите переименование сущностей (см.
[«Смена node_id»](#смена-node_id-почему-появляется-второе-устройство)), потом
настраивайте панель — конфигурация «Энергии» хранит идентификаторы статистик, и
переименование после настройки может их сломать.

## Панель «Электроэнергия» с вкладками

Встроенная панель «Энергия» показывает суммарные цифры и стоимость, но не даёт
разбивки по тарифам и периодам. Готовый пример своей панели лежит в репозитории:

| Файл | Куда вставлять |
| --- | --- |
| [`examples/energy_helpers.yaml`](../examples/energy_helpers.yaml) | блоки `input_number`, `utility_meter`, `sensor` — в `configuration.yaml` (или создать те же вспомогательные элементы через интерфейс) |
| [`examples/energy_dashboard.yaml`](../examples/energy_dashboard.yaml) | целиком в **Raw-редактор** нового дашборда (**Настройки → Панели → Добавить панель → Новый из пустого → ⋮ → Редактировать панель → ⋮ → Raw-редактор**) |

Панель состоит из четырёх вкладок (в Home Assistant вкладки — это представления
дашборда):

| Вкладка | Что показывает | Откуда данные |
| --- | --- | --- |
| Текущие сутки | расход и стоимость по тарифам за сегодня, столбцы по часам, мгновенные значения | суточные счётчики `utility_meter` + статистика накопительных сенсоров |
| Текущий месяц | расход и стоимость по тарифам с 1-го числа | `ET0PE` минус `ENMPE` |
| Предыдущий месяц | расход и стоимость за прошлый месяц, столбцы по месяцам | `ENMPE` минус `ENMPE_PREV` (архивные записи счётчика) |
| Предыдущие 7 суток | **столбчатый график** расхода по суткам, отдельно по тарифам и суммарно, плюс итоги и стоимость | скользящее окно по накопительным сенсорам (вспомогательные элементы «Статистика») |

Стоимость считается прямо в карточках: расход за период умножается на цену из
`input_number.tariff_t1…t3`, поэтому менять тариф можно в любой момент без правки
шаблонов. Валюта берётся из **Настройки → Система → Общие → Валюта**.

Про «расход за последние 7 суток» в карточке устройства: отдельных суточных
сущностей счётчика в режиме `array` нет (суточный архив лежит кольцом, см.
[«Режим array»](#режим-array-массив-общего-чтения)), поэтому сутки считаются из
накопительной энергии: Home Assistant пишет долговременную статистику по `ET0PE`,
а карточка `statistics-graph` с `stat_type: change` и `period: day` показывает
расход по каждому дню. Этот способ точнее архива счётчика: он включает текущие,
ещё не завершённые сутки.

Перед вставкой дашборда проверьте идентификаторы сущностей (в примере
предполагаются `sensor.energomera_ce301_active_energy_*`) — их можно посмотреть в
**Настройки → Устройства и службы → Объекты**. Шаблоны удобно проверять в
**Инструменты разработчика → Шаблон**.

## Команды счётчика

### Быстрое выборочное чтение (используется по умолчанию)

П. 5.3.2 инструкции. Команда выполняется **вне сеанса**, поэтому не требует
идентификации счётчика, смены режима и пароля:

```text
/?!<SOH>R1<STX>ИМЯ(аргумент)<ETX><BCC>      — безадресная
/?адрес!<SOH>R1<STX>ИМЯ(аргумент)<ETX><BCC> — адресная
```

Аддон использует безадресную форму. Аргумент в скобках пуст для параметров без
аргумента (`ET0PE()`, `POWEP()`, `VOLTA()`, `CURRE()`) и содержит месяц или дату
для архивов (`ENMPE(09.26)`, `EADPE(07.10.26)`, `MAXPE(10.26)`).

Контрольная сумма `BCC` считается по телу кадра (`<SOH>R1<STX>…<ETX>`) как
`сумма байт & 0x7F` — так же, как в библиотеке `IEC61107_py`.

Ответ: `<STX>данные<ETX><BCC>`. Из содержимого между `STX` и `ETX` извлекаются все
числа в круглых скобках. Например, ответ `ET0PE(53309.45)(9342.39)(33230.18)`
даёт список `[53309.45, 9342.39, 33230.18]`, который раскладывается по тарифам в
порядке `total`, `t1`, `t2`, ….

### Сессионное чтение (read_mode: session)

Поведение версии 1.0.4: `/?!<CR><LF>` → идентификация → `ACK 0 <скорость> 1
<CR><LF>` (режим программирования) → команды `<SOH>R1<STX>ИМЯ()<ETX><BCC>`, при
необходимости после `<SOH>P1<STX>(пароль)<ETX><BCC>`. Архивные параметры и в этом
режиме читаются безадресными кадрами, так как требуют аргумента.

### Параметры и форматы аргументов (таблица А.1)

| Параметр | Смысл | Аргументы |
| --- | --- | --- |
| `EXYZT` | Энергия, где `XY`: `T0` — нарастающим итогом, `NM` — на конец месяца, `ND` — на конец суток, `AM` — за месяц, `AD` — за сутки; `Z`: `P` — активная, `Q` — реактивная; `T`: `E` — потреблённая, `I` — отпущенная | `()` весь массив; `(мм.гг)` месяц по всем тарифам; `(мм.гг.нн.nn)` по конкретному тарифу; `(дд.мм.гг)` сутки по всем тарифам |
| `MAXyz` | Максимальные значения мощности по каждому тарифу (5 значений) | `()` весь массив; `(мм.гг)` за месяц по всем тарифам |
| `POWEz` | Мгновенная суммарная мощность, `z`: `P` — активная, `Q` — реактивная | `()` |
| `VOLTA` | Действующее значение напряжения, три параметра: A, B, C (В) | `()` |
| `CURRE` | Действующее значение тока, три параметра: A, B, C (А) | `()` |

В коде аддона имя параметра складывается из шаблона: `ET0PE` = `E`+`T0`+`P`+`E`,
`ENMPE` = `E`+`NM`+`P`+`E`, `EADPE` = `E`+`AD`+`P`+`E`, `MAXPE` = `MAX`+`P`+`E`.

### Коды ошибок (п. 5.3.3.5)

| Код | Значение |
| --- | --- |
| `E05` | ошибка протокола |
| `E12` | неподдерживаемый параметр |
| `E17` | недопустимое значение аргумента запроса |
| `E18` | отсутствует параметр, определяемый значением аргумента |
| `E22` | размер запрошенной информации превышает размер выходного буфера |

Аддон распознаёт эти коды и пишет в журнал расшифровку, например:
`Meter returned error: 0005(E12) [E12 — неподдерживаемый параметр]`.

## Режимы опроса

Аддон использует два независимых интервала:

- **Быстрый** (`poll_interval`) — энергия, мощность, напряжение, ток.
  Читается каждый цикл.
- **Медленный** (`slow_poll_interval`) — архивы `ENMPE`, `EADPE` ×7, `MAXPE`.
  Читается только если с прошлого медленного опроса прошло не меньше
  `slow_poll_interval` секунд; счётчик времени хранится в памяти процесса, поэтому
  после перезапуска аддона архивы читаются сразу.

Каждый цикл — отдельное TCP-соединение: подключение → чтение всех включённых
параметров → закрытие сокета. В режиме `session` дополнительно выполняется
`end_session()`, который завершает сеанс и делает паузу 2 секунды; в режиме `fast`
сессия не открывается, поэтому этой паузы нет.

Практические рекомендации по интервалам:

| Сценарий | `poll_interval` | `slow_poll_interval` |
| --- | --- | --- |
| Детальный мониторинг нагрузки | 10–30 | 3600 |
| Обычный режим | 60 | 3600 |
| Экономия ресурса счётчика и щадящий режим шлюза | 300–600 | 21600–86400 |

### Режим array (массив общего чтения)

Для счётчиков, которые не отвечают на быстрое выборочное чтение вне сеанса
(проверено на CE301 v11: он игнорирует и безадресные, и адресные кадры), есть
режим `array`:

1. открывается сеанс обмена: `/?!<адрес>!<CR><LF>` — счётчик отвечает
   `/EKT5CE301v11`;
2. отправляется ACK с переходом в режим чтения: `0 <скорость> 0 <CR><LF>`;
3. счётчик сам отдаёт весь массив параметров — около 30 КБ за 40 секунд (у CE301
   это 177 имён), кадр заканчивается `!<CR><LF><ETX><BCC>`;
4. аддон читает массив **только до последнего нужного ему параметра** и обрывает
   поток: на CE301 это ≈16 КБ за ≈21 с вместо 30 КБ за ≈42 с. Остаток массива —
   служебные `GRF`, `CHS`, `LISTR`, они аддону не нужны. Если счётчик отдал
   меньше записей архива, чем ожидается, массив дочитывается до конца;
5. значения публикуются в те же топики, что и в других режимах; сеанс
   закрывается командой `B0`, если массив был дочитан полностью.

Публикуются:

| Параметр из массива | Куда попадает |
| --- | --- |
| `ET0PE` (6 значений) | `{topic_prefix}/et0pe/{total,t1…t5}` |
| `POWEP` | `{topic_prefix}/powep` |
| `VOLTA` (3) | `{topic_prefix}/volta/{a,b,c}` |
| `CURRE` (3) | `{topic_prefix}/curre/{a,b,c}` |
| `ENMPE` (12 записей × 6) | `{topic_prefix}/enmpe/{total,t1…t5}` — последний завершённый месяц |
| `ENMPE` на месяц раньше | `{topic_prefix}/enmpe_prev/{total,t1…t5}` — показание на начало предыдущего месяца; разница с `enmpe` даёт расход за прошлый месяц |
| `MAXPE` (12 записей × 5) | `{topic_prefix}/maxpe/{t1…t5}` — из той же записи месячного кольца |
| `SNUMB` | `{topic_prefix}/serial` — заводской номер, диагностическая сущность «Serial number» |

Особенности:

- **Заводской номер и сведения об устройстве.** `SNUMB`, `IDPAS`, `IDENT` и
  `MODEL` лежат в самом конце массива (`SNUMB` — на 99,5 % потока), куда обычный
  цикл с обрывом на 52 % не доходит. Поэтому при первом запуске и далее раз в
  сутки один цикл дочитывает массив до конца (≈42 с) и сохраняет найденное в
  `/data/device_info.json`. Номер попадает в карточку устройства как поле
  «Серийный номер» (discovery публикуется заново, когда номер получен) и в
  диагностический сенсор «Serial number» в разделе «Диагностика». Отключается
  опцией `read_device_info: false`.
- **Порядок параметров в потоке** (замерено на CE301 v11, доля прочитанного
  массива, на которой параметр появляется):

  | Параметр | Где в потоке |
  | --- | --- |
  | `ET0PE` (энергия) | 0 % |
  | `ENMPE` (энергия на конец месяца) | 1 % |
  | `EADPE` (суточный расход) | 31 % |
  | `MAXPE` (максимумы мощности) | 45 % |
  | `POWEP`, `CURRE`, `VOLTA` (мощность, ток, напряжение) | 51 % |
  | `IDENT`, `ID_FW` (модель и версия ПО) | 73 % |
  | `CONDI`, `IDPAS`, `SNUMB`, `MODEL` (адрес, заводской номер) | 99 % |

  Отсюда важное следствие: **разделить опрос на «частый» и «редкий» по времени
  чтения нельзя**. Максимумы мощности приходят в потоке раньше токов и
  напряжений, поэтому любой запрос, который доходит до мощности и фаз, уже
  содержит и архивы. А сам счётчик отдаёт массив целиком и занимает шину около
  42 с независимо от того, когда мы перестали слушать.
- **Интервал опроса.** Ставьте `poll_interval` не меньше 90–120 с: если
  подключиться, пока счётчик ещё докачивает массив, ответ на идентификацию
  придёт хвостом потока. Аддон это распознаёт, вычитывает остаток («Сброшено
  N байт незавершённого потока…») и повторяет идентификацию, но время цикла
  вырастет до полного чтения массива — выгода от обрыва пропадёт.
- **Месяц определяется по энергии.** Месячный архив счётчик отдаёт кольцевым
  буфером: порядок записей «повёрнут» относительно календаря (в замерах
  `[04]…[11]` = окт-2025…май-2026, `[00]…[03]` = июн…сен-2026). Энергия монотонно
  растёт, поэтому последний завершённый месяц — запись с наибольшим итогом, не
  превышающим текущий. Так архив разбирается корректно при любом сдвиге кольца.
- **Максимумы мощности** берутся из той же записи, что и месяц: оба архива
  месячные и сдвигаются синхронно. Если записей `MAXPE` меньше, чем `ENMPE`,
  значение не публикуется.
- **Суточный архив (`EADPE`) не публикуется.** Его 45 записей тоже лежат кольцом,
  но суточный расход не монотонен, и сдвиг кольца по данным не восстанавливается
  (проверено: расход за текущий месяц не набирается ни одним 5–6-суточным окном).
  Сущности `eadpe_d*` исключаются из discovery; суточное потребление считается в
  Home Assistant из накопленной энергии — например, через `utility_meter` или
  долговременную статистику.
- **Один опрос — одно обращение.** Массив содержит всё сразу, поэтому
  `slow_poll_interval` в этом режиме не используется: все публикуемые параметры
  (включая месячные архивы) приходят за один цикл ≈21 с. При `poll_interval: 120`
  счётчик занят примерно треть времени.
- **Если оперативные величины не нужны** — отключите `read_power`, `read_voltage`
  и `read_current`: нужные параметры окажутся ближе к началу потока, и обрыв
  произойдёт раньше. С `read_energy` и `read_monthly_archive` цикл занимает
  ≈13 с, с одной только `read_energy` — меньше секунды.
- **Таймаут.** `poll_timeout` должен покрывать вычитку массива: для CE301 хватает
  90 с, при медленном шлюзе ставьте больше (до 300).

Пример настроек для CE301 v11 через TCP-шлюз:

```yaml
read_mode: "array"
poll_interval: 120
poll_timeout: 90
```

## Диагностика и частые проблемы

### Как включить подробный журнал

Опция `log_level: debug` (вкладка «Настройки» аддона) включает кадры обмена в HEX,
тайминги отправки и приёма, содержимое ответов, разбор ошибок и трассировки
стеков. При запуске вне Supervisor то же самое даёт
`python3 meter_bridge.py --debug` или переменная окружения
`METER_BRIDGE_LOG_LEVEL=debug`.

При старте аддон всегда печатает действующую конфигурацию (пароли — в виде
`*** (N симв.)`): адрес и порт шлюза, режим чтения, адресность кадров, чётность,
таймаут, MQTT-брокер, интервалы и список читаемых параметров. Это первое, что
стоит сверить при проблемах: часто выясняется, что пришёл не тот хост, порт или
режим.

Полезные строки уровня `info`:

| Строка в журнале | Что означает |
| --- | --- |
| `TCP: соединение с <хост>:<порт> установлено за N с` | шлюз доступен по сети |
| `TCP: таймаут N с — от <хост>:<порт> не пришло ни одного байта…` | соединение есть, но счётчик не отвечает |
| `Read <КОМАНДА> (<ключ>) = [...] за N с` | ответ получен и разобран |
| `Опубликовано значений: N (прочитано ключей: M)` | сколько данных реально ушло в MQTT |
| `Ни одно значение не опубликовано…` | ответ есть, но числа из него не извлеклись |

### Режим `--probe`: проверка канала без MQTT

Если чтение падает с таймаутом, запустите автономную диагностику:

```bash
python3 meter_bridge.py --probe     # вне Supervisor; /data/options.json уже есть
```

Что делает режим:

1. подключается к `meter_host:meter_port` и печатает время установки соединения;
2. пассивно слушает 3 секунды — некоторые шлюзы сами присылают баннер;
3. по очереди отправляет кадр чтения `ET0PE` в четырёх вариантах — безадресный и
   адресный, с эмуляцией чётности 7E1 и без неё — и печатает HEX отправленного и
   принятого;
4. «провоцирует» шлюз строками `<CR><LF>`, `/?!<CR><LF>` и запросом сеанса
   `/?<адрес>!<CR><LF>`;
5. по результату подсказывает, какую опцию включить (`use_address`,
   `emulate_parity`), либо перечисляет причины молчания.

MQTT в этом режиме не используется, счётчик не программируется: уходят только
запросы чтения.

Типичные исходы:

| Результат `--probe` | Вывод |
| --- | --- |
| `TCP-соединение НЕ установлено` | неверный `meter_host`/`meter_port`, шлюз выключен или порт занят другой программой |
| Ответ только на адресный кадр | включите `use_address: true` |
| Ответ только на вариант 8N1 | установите `emulate_parity: false` |
| Ответа нет ни на один быстрый кадр, но есть ответ на идентификацию `/?!<CR><LF>` | счётчик не поддерживает быстрое выборочное чтение вне сеанса — см. [«Что показала диагностика CE301»](#что-показала-диагностика-ce301) |
| После ACK счётчик отдаёт массив общего чтения | сеанс и линия работают; проба сохраняет массив в `probe_session_0.log` |
| Шлюз закрывает соединение после кадра | кадр отвергнут: не тот адрес, режим или протокол шлюза |
| Ответ есть, но значения пусты | смотрите предупреждения разбора: `Meter returned error: …`, `в ответе нет чисел в круглых скобках` |

### Что показала диагностика CE301

Замеры на связке CE301 (прошивка `v11`) и TCP-шлюза, выполненные режимом `--probe`:

| Проверка | Результат |
| --- | --- |
| TCP-соединение со шлюзом | устанавливается за 0,02 с, порт живой |
| Быстрое выборочное чтение вне сеанса (`/?!…`, `/?<адрес>!…`, 7E1 и 8N1) | **ответа нет ни на один вариант** — счётчик такие кадры игнорирует |
| Запрос идентификации `/?!<CR><LF>` | отвечает `/EKT5CE301v11` (Энергомера, скорость 9600, CE301, v11) |
| `CONDI` | `3328`: бит 0 = 0 (беспарольное выборочное чтение разрешено), бит 8 = 1 (программирование без «ДСТП» разрешено) |
| Сеанс в режиме чтения (ACK `0` `<скорость>` `0` `<CR><LF>`) | счётчик сам отдаёт **весь массив параметров**: ~30 КБ, ~40 с (≈750 байт/с), 177 имён, заканчивается `!<CR><LF><ETX><BCC>` |
| Сеанс в режиме программирования (ACK `…1…`) | отвечает коротким кадром `<SOH>P0<STX>(777777)<ETX><BCC>` и массив не отдаёт |

В массиве общего чтения есть все параметры, которые нужны аддону:

| Параметр в массиве | Сколько значений | Что это |
| --- | --- | --- |
| `ET0PE` | 6 | энергия: суммарная + тарифы T1…T5 |
| `POWEP` | 1 | мгновенная активная мощность |
| `VOLTA` | 3 | напряжение фаз A, B, C |
| `CURRE` | 3 | ток фаз A, B, C |
| `ENMPE` | 72 | 12 месяцев × 6 значений (энергия на конец месяца) |
| `EADPE` | 270 | 45 суток × 6 значений (расход за сутки) |
| `MAXPE` | 60 | 12 месяцев × 5 значений (максимумы по тарифам) |
| `SNUMB` | 1 | заводской номер счётчика, например `00608763` |

**Вывод.** У этой связки работает только сеансовый режим, причём данные приходят
не ответами на отдельные запросы параметров, а одним массивом общего чтения после
ACK с переходом в режим чтения. Ни `read_mode: fast` (кадры вне сеанса счётчик
игнорирует), ни `read_mode: session` (вход в режим программирования и затем
отдельные запросы `R1`) с этим счётчиком данные не дают: в режиме
программирования счётчик ждёт кадр пароля и на запросы параметров не отвечает.
Массив отдаётся медленно, поэтому для его вычитки нужен `poll_timeout` порядка
60–120 секунд, а интервал опроса — не меньше нескольких минут.

Именно этот механизм реализует `read_mode: array` — см.
[«Режим array»](#режим-array-массив-общего-чтения).

### Частые проблемы

### Аддон сразу останавливается

```text
No options found. This add-on must run under Home Assistant Supervisor.
```

Файл `/data/options.json` отсутствует. Это происходит при запуске контейнера вручную
(`docker run`) вместо Supervisor.

### `exec: fatal: unable to exec bashio`

```text
exec: fatal: unable to exec bashio
: No such file or directory
```

В `run.sh` попали окончания строк CRLF: шебанг превращается в
`#!/usr/bin/with-contenv bashio<CR>`, ядро ищет интерпретатор с именем `bashio\r`
и не находит его — отсюда и перенос строки посреди сообщения об ошибке. Так
бывает, если файл сохранён или скопирован на Windows (VS Code, «Блокнот»,
Samba-шара).

Что делать:

1. Проверить: `cat -A /addons/<папка-аддона>/run.sh | head -1` — строка должна
   заканчиваться `$`, а не `^M$`.
2. Привести файл к LF: `sed -i 's/\r$//' /addons/<папка-аддона>/run.sh` — или
   заново скопировать из репозитория, где в `.gitattributes` закреплено
   `*.sh text eol=lf`.
3. Пересобрать аддон.

В `Dockerfile` есть страховка: `run.sh` нормализуется (`tr -d '\r'`) и
запускается через `CMD [ "/bin/sh", "/run.sh" ]`, поэтому CRLF в исходнике уже
не мешает запуску и `bashio` в базовом образе не требуется. Страховка работает
только при актуальном `Dockerfile` в папке аддона.

### Нет подключения к MQTT

```text
MQTT connect to <host>:<port> failed (...), retry in 5 s
```

Аддон не падает, а повторяет попытки. Проверьте:

1. `mqtt_host` и `mqtt_port`. При `host_network: true` `localhost` указывает на хост
   Home Assistant; порт должен совпадать с реальным портом брокера
   (у аддона Mosquitto по умолчанию `1883`).
2. `mqtt_user` / `mqtt_password` — учётные данные должны существовать в брокере
   (в Mosquitto — список `logins`). По умолчанию оба поля пусты.
3. `mqtt_tls` должен соответствовать порту: для TLS-порта включайте флаг,
   для обычного `1883` — выключайте.

### Ошибки чтения параметров

```text
TCP: таймаут 15.0 с — от 192.168.10.250:1111 не пришло ни одного байта с терминатором 0x03. …
Failed to read ET0PE (ET0PE) за 15.001 с: GatewaySilentError: таймаут 15.0 с: ответ не получен
```

Порядок действий:

1. Запустите `python3 meter_bridge.py --probe` (вне Supervisor) — он отличит
   «шлюз не отвечает вообще» от «шлюз не понимает кадр» (см. таблицу исходов
   выше).
2. Проверьте `meter_host` / `meter_port` — доступен ли шлюз, тот ли это порт.
3. Увеличьте `poll_timeout` до 30–60 секунд, если шлюз заведомо медленный.
4. Сверьте `meter_address` — сетевой адрес счётчика (IDPAS). В режиме `fast` он
   участвует в кадре только при `use_address: true`.
5. Убедитесь, что шлюз не занят другой программой: TCP-шлюзы обычно принимают
   одного клиента.

### `Meter returned error: … (E12/E18)`

Для `ENMPE`, `EADPE`, `MAXPE` это чаще всего означает, что в счётчике нет данных за
запрошенный период (например, суточный архив ещё не сформирован), либо что команда
не поддерживается конкретным исполнением счётчика. `E12` — неподдерживаемый
параметр, `E18` — отсутствует параметр с таким аргументом, `E17` — недопустимый
аргумент.

### Сущности не появились в Home Assistant

1. Убедитесь, что интеграция **MQTT** настроена и указывает на тот же брокер.
2. Префикс discovery в Home Assistant должен быть `homeassistant` — он зашит в коде
   константой `DISCOVERY_PREFIX` и не настраивается.
3. Посмотрите retained-топики `homeassistant/sensor/meter_<адрес>/#` любым
   MQTT-клиентом (например, MQTT Explorer). Если топиков нет — аддон не смог
   подключиться к брокеру.
4. Discovery публикуется при подключении к брокеру. После изменения опций, особенно
   флагов `read_*` и `node_id`, перезапустите аддон.

### Сущности «недоступны» (unavailable)

Так и должно быть, если аддон потерял связь со счётчиком: в `{topic_prefix}/status`
публикуется `offline`, и все сущности переходят в статус «недоступно». Если статус
не восстанавливается:

- проверьте журнал аддона на строки `Poll cycle failed`;
- убедитесь, что MQTT-брокер доступен (`MQTT disconnected` в журнале);
- проверьте, что топик `{topic_prefix}/status` не перезаписывается другим
  устройством с тем же `topic_prefix`.

### «Залипшие» и дублирующиеся сущности

Значения публикуются с `retain`, поэтому:

- после выключения флага `read_*` ранее опубликованное значение остаётся в брокере —
  удалите соответствующий топик вручную;
- после изменения `topic_prefix` в брокере остаётся целое дерево старых топиков;
- после изменения `meter_address` или `node_id` меняется `unique_id`, поэтому
  появляется новое устройство, а старые сущности становятся «недоступными» и
  удаляются вручную.

Чтобы вычистить всё разом, удалите retained-топики
`homeassistant/sensor/meter_<старый_адрес>/#` и `<старый_topic_prefix>/#`,
затем перезапустите аддон.

### Обновление с версии 1.0.5

Поведение по умолчанию не изменилось: новые опции `use_address: false` и
`emulate_parity: true` воспроизводят прежний формат кадров, а `read_mode` по
умолчанию остаётся `fast`. Добавлены опция `log_level`, режим `--probe` и
подробный журнал (см. [«Диагностика и частые проблемы»](#диагностика-и-частые-проблемы)),
а также третий режим чтения — `read_mode: array`, который работает на счётчиках,
игнорирующих быстрое выборочное чтение (см.
[«Режим array»](#режим-array-массив-общего-чтения)). Также исправлено чтение
`/data/options.json` с BOM и разбор ответов без терминатора `ETX` — из-за
последнего значения могли молча не публиковаться.

### Обновление с версии 1.0.4

- Появился тариф T5 у `ET0PE`, `ENMPE`, `EADPE` (шесть значений вместо пяти).
- Суффикс суммарной энергии суточного архива (`eadpe_dN/total`) не изменился;
  изменилось только отображаемое имя сущности (было «…сумма», стало «…total»).
- Появились сущности-дубликаты, если `meter_address` изменить нельзя, а `node_id`
  ранее не задавался — не требуется: `node_id` по умолчанию остался прежним
  (`meter_<адрес>`).
- Режим чтения по умолчанию — `fast`. Если счётчик или шлюз работают только в
  сессии, верните `read_mode: session`.

## Известные ограничения

| # | Ограничение | Последствия |
| --- | --- | --- |
| 1 | Режим `session` требует разрешения программирования (`CONDI`, бит 8, или нажатие «ДСТП») | Для таких счётчиков подходит `read_mode: array`; `fast` работает не на всех прошивках |
| 2 | Discovery публикуется при подключении к брокеру, но не при изменении опций | После правки опций нужен перезапуск аддона |
| 3 | Значения публикуются с `retain` | Отключение флага `read_*` не убирает старые значения из брокера |
| 4 | `unique_id` зависит от `node_id` / `meter_address` | Смена идентификатора создаёт новое устройство в Home Assistant |
| 5 | Суточный архив ограничен 7 днями (`EADPE` ×7) | Более глубокая история недоступна |
| 6 | Имена сущностей английские, области — с префиксом `et0pe`/`powep`/… | Неоднородный вид в русскоязычном интерфейсе |
| 7 | У двунаправленных счётчиков `POWEP` может выдавать два значения (потребление и генерация) | Публикуется только первое (потребление) |
| 8 | `state_class` суточного расхода — `total`, у остальных энергий — `total_increasing` | Различия в статистике долговременного хранения |
| 9 | Библиотека `IEC61107_py` не обновлялась с 2022 г. | Сборка зависит от внешнего GitHub-репозитория; при его удалении сборка сломается |
| 10 | Базовый образ закреплён тегом, а не дайджестом | Возможны изменения внутри того же тега |
| 11 | Профиль AppArmor основан на официальном шаблоне и намеренно не ужесточён (`file,`) | Рейтинг безопасности 5 из 6; монтирование, `ptrace` и прочие опасные операции всё равно запрещены |
| 12 | В репозитории нет автоматических тестов | Регрессии выявляются только вручную |
| 13 | В режиме `array` суточный архив (`EADPE`) не публикуется | Суточное потребление считайте в Home Assistant из накопленной энергии (`utility_meter` или статистика) |
| 14 | В режиме `array` максимумы мощности берутся из той же записи месячного кольца, что и энергия на конец месяца | Если в конкретном счётчике месячные архивы сдвигаются не синхронно, максимумы могут относиться к другому месяцу |
| 15 | В режиме `array` цикл опроса занимает ≈21 с, а шину счётчик занимает ≈42 с (массив до конца уже не читается) | `poll_interval` держите не меньше 90 с, иначе аддон будет вычитывать хвост массива и цикл растянется до полного |
| 16 | Образы собираются GitHub Actions и публикуются в GHCR | Пока workflow не отработал и пакет в GHCR не сделан публичным, установка из репозитория не сможет скачать образ (см. [«Публикация и обновление»](#публикация-и-обновление)) |

## Структура репозитория

Репозиторий — это репозиторий приложений Home Assistant: в корне лежит
`repository.yaml`, а каждое приложение — в своей папке
([требование документации](https://developers.home-assistant.io/docs/apps/repository/)).
Сейчас в нём одно приложение:

```text
EnergomeraMeterBridge/                  # корень репозитория
├── repository.yaml                     # описание репозитория (имя, url, maintainer)
├── LICENSE                             # MIT
├── README.md                           # описание репозитория и установка
├── .gitattributes                      # окончания строк: .sh и Dockerfile — LF
├── .gitignore
├── .github/workflows/builder.yaml      # сборка и публикация образов в GHCR
├── examples/                           # примеры панели «Электроэнергия» и вспомогательных сущностей
├── _source/                            # исходные картинки в высоком разрешении (не публикуются)
└── energomera_meter_bridge/            # папка приложения
    ├── config.yaml                     # опции, схема, архитектуры, image, url
    ├── Dockerfile                      # образ приложения (+ метки io.hass.*)
    ├── run.sh                          # точка входа
    ├── meter_bridge.py                 # логика опроса и публикации
    ├── DOCS.md                         # эта документация (вкладка «Документация»)
    ├── README.md                       # витрина приложения в магазине
    ├── CHANGELOG.md                    # история изменений
    ├── LICENSE                         # копия лицензии для самодостаточности папки
    ├── apparmor.txt                    # профиль AppArmor (+1 балл безопасности)
    ├── icon.png                        # иконка 128×128 (требование: 1:1)
    ├── logo.png                        # логотип 250×193 (рекомендуют ~250×100)
    └── translations/
        ├── ru.yaml                     # названия и описания опций (русский)
        └── en.yaml                     # названия и описания опций (английский)
```

Имя папки приложения роли не играет — Supervisor находит приложение по
`config.yaml` внутри неё, а идентификатор берётся из `slug` (`meter_bridge`).
Папка `_source/` держит исходные картинки высокого разрешения и исключена из git
через `.gitignore`.

## Публикация и обновление

Официальный магазин Home Assistant собирается из репозитория команды Home
Assistant, поэтому сторонние приложения распространяются **через свой репозиторий**:
пользователь один раз добавляет адрес в магазине (**⋮ → Репозитории**), после чего
приложение и его обновления появляются в общем списке как обычные.

Что для этого нужно:

1. Публичный git-репозиторий с `repository.yaml` в корне и папкой приложения —
   структура выше. Поля `repository.yaml`: `name` (обязательно), `url`,
   `maintainer`.
2. В `config.yaml` заполнены обязательные поля (`name`, `version`, `slug`,
   `description`, `arch`) и `url` — ссылка на страницу приложения, которую
   магазин показывает как «Перейдите на страницу приложения … для получения
   дополнительной информации».
3. Иконка `icon.png` 1:1 (128×128) и логотип `logo.png` (~250×100), `README.md`
   (витрина), `DOCS.md` (документация), `CHANGELOG.md`.
4. Сборка — см. ниже.

### Готовые образы через GitHub Actions

Образы собирает [`.github/workflows/builder.yaml`](../.github/workflows/builder.yaml)
официальными builder-actions Home Assistant. Workflow запускается при пуше в
`main`, если изменилась папка приложения или сам workflow (плюс есть ручной
запуск **Actions → Builder → Run workflow**), и делает три шага:

1. **prepare** — читает `config.yaml` (`arch`, `image`, `version`, `name`,
   `description`, `url`) и готовит матрицу сборки;
2. **build** — параллельно собирает образы `amd64` и `aarch64`, подписывает их
   Cosign и публикует в GHCR как `ghcr.io/master-mishutka/amd64-energomera-meter-bridge`
   и `…/aarch64-…`;
3. **manifest** — объединяет их в multi-arch манифест
   `ghcr.io/master-mishutka/energomera-meter-bridge` с тегами `1.1.0` и `latest`.

Тег образа — это `version` из `config.yaml`, поэтому повторный пуш без поднятия
версии образ пересобирает, но не публикует (`skip-existing`): чтобы выпустить
изменения, поднимите версию.

Порядок первого запуска:

1. запушить репозиторий в GitHub и дождаться успешного прогона workflow
   (**Actions**);
2. **сделать пакет публичным**: GitHub → вкладка **Packages** → пакет
   `energomera-meter-bridge` → **Package settings** → **Change visibility** →
   **Public**. Пока пакет приватный, Supervisor не сможет скачать образ без
   авторизации, и установка упадёт;
3. только после этого добавлять репозиторий в Home Assistant.

Поле `image:` в `config.yaml` — переключатель: пока оно указано, Supervisor
скачивает готовый образ и **не** собирает Dockerfile на устройстве. Чтобы
проверить локальную сборку до первого релиза образов, закомментируйте `image:` —
тогда образ соберётся на самом устройстве.

Как выпустить обновление:

1. внести изменения в код и документацию;
2. поднять `version` в `config.yaml` (формат `X.Y.Z`, семантическое
   версионирование) и дописать раздел в `CHANGELOG.md`;
3. закоммитить и запушить в `main` — workflow соберёт и опубликует образ с новым
   тегом;
4. в Home Assistant обновить магазин (**⋮ → Проверить обновления**) и нажать
   **Обновить** у приложения. Пользователям с включённым автообновлением
   приложение обновится само.

Полезно помнить:

- `version` в `config.yaml` — единственный источник версии для магазина: она же
  тег образа в GHCR, поэтому они обязаны совпадать;
- для тестовых сборок удобно использовать ветку и подключать её как
  `https://github.com/<владелец>/<репозиторий>#next`
  ([документация](https://developers.home-assistant.io/docs/apps/presentation/));
- свой профиль `apparmor.txt` даёт балл безопасности (см.
  [«Безопасность»](#безопасность)); он уже добавлен, при ужесточении профиля
  отлаживайте его по журналу аудита;
- после публикации репозитория старое локальное приложение с тем же `slug`
  (`local_meter_bridge`) лучше удалить, чтобы не было двух приложений с
  одинаковым идентификатором.

## Сборка и локальная отладка

Базовый образ и зависимости (все версии зафиксированы):

```dockerfile
FROM ghcr.io/home-assistant/base-python:3.14-alpine3.24
RUN apk add --no-cache git

ARG IEC61107_COMMIT=473cbc9f3f8a11a184397e57b1be6465a01d1433

RUN pip3 install --break-system-packages --no-cache-dir \
    paho-mqtt==2.1.0 \
    pyserial==3.5 \
    "git+https://github.com/Ko1dun/IEC61107_py.git@${IEC61107_COMMIT}"
```

Чтобы обновить библиотеку, укажите новый SHA в `ARG IEC61107_COMMIT` или передайте
его при сборке: `--build-arg IEC61107_COMMIT=<sha>`.

Исходники должны быть в LF: `run.sh` с CRLF не запускается (см.
[«`exec: fatal: unable to exec bashio`»](#exec-fatal-unable-to-exec-bashio)).
За это отвечают правила в `.gitattributes`, а `Dockerfile` дополнительно
нормализует `run.sh` строкой `tr -d '\r'` и запускает его через `/bin/sh`.

Аддон требует доступа в интернет **на этапе сборки** — библиотека `IEC61107_py`
устанавливается из GitHub.

Запуск вне Supervisor для отладки: создайте файл `/data/options.json` с плоским
JSON-объектом, повторяющим структуру опций, и запустите `python3 meter_bridge.py`.
Без этого файла аддон завершится с ошибкой. Ключи командной строки:

| Команда | Что делает |
| --- | --- |
| `python3 meter_bridge.py` | обычный опрос и публикация в MQTT |
| `python3 meter_bridge.py --probe` | только диагностика канала до счётчика, без MQTT |
| `python3 meter_bridge.py --dump-array` | снять массив общего чтения, сохранить в `array_dump.log` и показать, на какой доле потока появляется каждый параметр |
| `python3 meter_bridge.py --debug` | подробный журнал: кадры обмена, байты, тайминги |
| `python3 meter_bridge.py --help` | справка |

Что учесть при таком запуске:

- **Путь.** Файл читается по абсолютному пути `/data/options.json`. В Linux это
  корень файловой системы, в Windows — корень текущего диска
  (`F:\data\options.json`, если проект лежит на диске `F:`).
- **Кодировка.** Файл может быть как без BOM (так пишет Supervisor), так и с BOM
  (так сохраняет PowerShell 5.1 или «Блокнот» с опцией BOM) — код читает его в
  `utf-8-sig` и принимает оба варианта. Комментарии `//` в JSON недопустимы.
- **MQTT.** `mqtt_host: "localhost"` работает только внутри аддона
  (`host_network: true`, то есть `localhost` — это хост Home Assistant). При
  запуске на другом компьютере укажите реальный адрес брокера и его порт.
- **Конфликт клиентов.** `client_id` зашит как `energomera_ce301_bridge`, поэтому
  перед локальной отладкой остановите аддон — иначе брокер будет поочерёдно
  отключать то аддон, то отладочный процесс.
- **Шлюз счётчика.** TCP-шлюз обычно принимает только одного клиента: при
  запущенном аддоне локальный процесс может получать таймауты.

Полезные точки для правки `meter_bridge.py`:

| Что | Где |
| --- | --- |
| Набор параметров и их метаданные | `build_parameters()` |
| Отображение опций в конфигурацию | `build_cfg_from_options()` |
| Открытие соединения и режим чтения | `open_meter()` |
| Сборка кадра чтения (адресный/безадресный) | `build_frame()` |
| Журналирование обмена и таймаутов | `LoggingTCP_transport` |
| Отправка кадра быстрого чтения | `send_raw_command()` |
| Разбор ответов счётчика | `parse_values_response()` |
| Чтение массива общего чтения (`read_mode: array`) | `read_all_from_array()`, `read_array_stream()` |
| Ожидание тишины в линии после обрыва массива | `drain_until_silence()` |
| Разбор массива и выбор месяца в кольцевом архиве | `parse_array_records()`, `values_from_array()` |
| Диагностика канала (`--probe`) | `run_probe()` |
| Сводка конфигурации при старте | `log_effective_config()` |
| Публикация discovery | `publish_discovery()` |
| Подключение к MQTT и повторные попытки | `build_mqtt_client()` |
| Основной цикл и интервалы | `main()` |

## Безопасность

Рейтинг безопасности Home Assistant считает от базы 5 из 6. У этого приложения
`host_network: true` (−1) и свой профиль AppArmor (+1) → **5 из 6**.

Профиль `apparmor.txt` лежит рядом с `config.yaml`, поэтому Supervisor загружает
его как основной профиль контейнера вместо `docker-default`. Он основан на
официальном шаблоне Home Assistant и дополнен тем, что нужно этому приложению:
запуск Python с библиотеками, разрешение имён (MQTT-брокер может задаваться
именем), корневые сертификаты для `mqtt_tls` и файлы дампов диагностики. Внутри
профиля запрещены монтирование, `ptrace` и прочие операции, которые обычному
пользовательскому процессу не нужны.

### Если понадобится ужесточить профиль

1. Добавьте в строку `profile meter_bridge flags=(…)` флаг `complain` —
   `flags=(attach_disconnected,mediate_deleted,complain)`: тогда отказы не
   блокируются, а только попадают в журнал аудита.
2. Перезапустите приложение, поработайте с ним (в том числе в режимах `--probe`
   и `--dump-array`) и посмотрите отказы на хосте Home Assistant:
   `journalctl _TRANSPORT="audit" -g 'apparmor="ALLOWED"'`.
3. Добавьте в профиль правила под эти пути и уберите `complain`, чтобы отказы
   снова блокировались.
4. Если после правки профиля контейнер не стартует — удалите или переименуйте
   `apparmor.txt` и пересоберите приложение: без файла используется
   `docker-default`, и приложение запустится.

Остальное:

- `host_network: true` нужен, чтобы видеть TCP-шлюз счётчика и брокер на
  `localhost`; без него пришлось бы указывать адреса явно, а шлюз счётчика может
  находиться в другой подсети.
- Приложение не запрашивает `docker_api`, `full_access`, `privileged`,
  `hassio_role` и доступ к файлам пользователя: из прав ему нужен только сетевой
  доступ.
- Пароли счётчика и MQTT хранятся в открытом виде в `/data/options.json` внутри
  контейнера — стандартное поведение приложений Home Assistant.
- Значения по умолчанию в `config.yaml` не содержат учётных данных: `mqtt_user` и
  `mqtt_password` пусты, `meter_password` содержит только заводское значение
  `777777`, опубликованное в инструкции.
- Для доступа к брокеру из внешней сети используйте `mqtt_tls: true`.
- Приложение только читает счётчик и никогда не программирует его; пароль
  администратора ему не нужен.
